# AMC 런칭 종합점검 의뢰서

**기준일:** 2026년 10월 13일  
**대상:** AMC / 고객 표시 브랜드 `allofmycareer`  
**수신:** 백엔드·프론트엔드·배포 및 운영 담당 엔지니어  
**범위:** 원래 브랜드 철학과 분석 프레임워크를 보존하면서 코드, 데이터 연결, 외부 정보, 분석 결과, 화면, 보고서, 배포, 운영 프로세스를 전체 점검합니다. **AMU는 이번 점검 대상이 아닙니다.**

**자료 확인 범위:** 최신 GitHub PR, 해당 커밋의 소스, 저장소 문서와 기존 AMC 설계 자료를 확인했습니다. 아래 운영 로그와 고객 제출 인쇄본의 관찰 내용은 PR #92의 검수 기록에 근거합니다. 이번 의뢰서 작성 과정에서 운영 환경 재실행, 유료 API 호출, 데이터베이스 조회·변경, 배포는 수행하지 않았습니다.

**참고:** PR #92에는 2026년 10월 13일 기준 출시 보류(STOP-SHIP)가 명시돼 있습니다. 앞선 “테스트 준비 완료” 기록보다 이 판단을 우선합니다.

## 1. 의뢰 목적

AMC는 새로운 화면을 더 만드는 것보다, **이미 설계된 서비스가 왜 실제 고객 사례에서 충분한 분석과 완성된 결과물을 제공하지 못하는지 규명해야 하는 단계**입니다.

다음 전체 흐름을 추적해 주십시오.

```text
고객 입력
→ 외부 정보 확보
→ 구조 분석
→ 고객 조건과 근거를 연결한 해석
→ 대시보드와 시뮬레이터
→ 최종 보고서
→ 운영 기록
```

각 단계에서 무엇이 실제 실행되고, 무엇이 고정 문구·대체 응답·미연결 상태인지 구분해야 합니다. 증상을 재현한 뒤 원인을 확인하고 수정하며, 같은 문제가 반복되지 않도록 회귀 테스트와 출시 기준을 남겨야 합니다.

**빌드 성공, 배포 Ready, 테스트 개수, 화면 표시 여부만으로 완료를 판단하지 마십시오. 실제 고객 입력에서 의미 있는 분석과 사용 가능한 보고서가 나오는지가 기준입니다.**

## 2. 브랜드 철학과 현재 제품 범위

### 2.1 AMC가 제공하려는 가치

AMC의 출발점은 **All of My Career**이며, 현재 고객 표시 브랜드는 소문자 **`allofmycareer`**입니다. 내부 코드·경로·프레임워크에는 AMC라는 이름이 남아 있습니다.

핵심 철학은 **Structure First**입니다.

AMC는 고객 대신 진로를 결정하거나, 특정 선택을 추천하거나, 일반적인 동기부여·상담 문구를 제공하는 서비스가 아닙니다. 다음을 드러내는 서비스입니다.

> 무엇을 지키고 무엇을 얻으려는 선택인지, 위험과 제약이 어디에 집중되는지, 무엇이 아직 확인되지 않았는지, 어떤 조건이 달라지면 선택의 구조가 달라지는지.

따라서 결과가 단순한 입력 요약이나 회사·학교 검색 목록이어서는 안 됩니다. **고객 조건과 외부 근거를 연결한 구조적 해석**이 있어야 합니다. 원래 설계에서도 고객 대신 결정하거나 추천하는 표현을 금지하고 있습니다.

### 2.2 보존해야 할 방향

분석은 AMC의 원래 프레임워크와 규칙을 중심으로 작동해야 합니다. 외부 AI와 검색은 공개 근거를 확보하는 수단이지, AMC를 임의의 상담 엔진으로 대체하는 장치가 아닙니다.

`Current Structural Posture`는 **조건부 구조 해석**이지 행동 명령이 아닙니다. 내부 코드에 옛 `Verdict`나 `Go` 계열 값이 남아 있더라도 고객 화면에 권고 문구로 다시 노출하지 않습니다.

시각적으로는 차분하고 밀도 있는 전문 분석 보고서를 지향합니다. 화려한 점수 카드, 게임식 표현, 과장된 확신을 피합니다. 인터랙티브 경험을 개선하더라도 분석 체계까지 바꾸지 않습니다.

### 2.3 과거 상품 기획과 현재 출시 범위를 구별할 것

현재 방향은 **무료 단일 고객 흐름**입니다. PR #81에서는 고객 화면의 요금제 구분, 챗봇, 형식 선택, 결제 연결 흐름을 제거했습니다. 과거 Essential/Executive와 보고서 연계 Q&A 기획은 **이력이지 현재 복구해야 할 필수 기능 목록이 아닙니다.**

일부 오래된 운영 문서에는 과거 요금제와 Q&A 정책이 남아 있습니다. 문서가 존재한다는 이유만으로 최신 정책으로 적용하지 마십시오.

결제·구독·Q&A 재도입과 현재 분석 품질 복구를 분리해야 합니다. **JEV도 최신 기록상 비활성이므로 이번 점검을 이유로 활성화하지 않습니다.**

## 3. 반드시 이해해야 할 분석 프레임워크

### 3.1 D1–D5와 FIFWM은 서로 다른 체계

원래 Python 엔진의 D1–D5는 다음과 같습니다.

| 구분 | 원래 명칭 | 분석 대상 |
|---|---|---|
| D1 | Market & Role | 목표 역할·분야의 수요와 개인의 차별성 |
| D2 | Company Stability & Governance | 회사의 건전성·안정성·조직 변화 |
| D3 | FIFWM Structural Risk | 지원 관계, 의사결정 체계, 업무 흐름, 시장·정책 노출 |
| D4 | Personal Fit & Temperament | 상방·하방 선호, 위험 수용, 실행·확약 성향 |
| D5 | Upside vs Downside | 현상 유지 시나리오와 안전망 |

원래 엔진에는 각 항목을 0–2로 만드는 계산과 합계 0–10이 있습니다. 다만 **원래 엔진이 존재한다는 사실과 현재 웹 입력에서 그 엔진이 정상 연결돼 있다는 것은 다릅니다.** 현재 V3 Posture의 support 계산도 옛 D1–D5 합계와 별개입니다.

### 3.2 FIFWM의 다섯 요소

FIFWM은 **Formal, Informal, Framework, Workflow, Market-Policy**입니다. 고객에게는 설명 없는 약어보다 다음 표현으로 전달하도록 정의돼 있습니다.

| 내부 요소 | 고객 표현 | 원래 평가 질문이 확인하는 대상 |
|---|---|---|
| Formal | 기회의 조건 | 목표 직무의 의사결정·보고 체계 이해 |
| Informal | 연결 가능성 | 목표 팀에서 성공을 적극 지원할 관리자·선임 존재 |
| Framework | 구조 적합성 | 최근 2~3년 조직 개편·리더십 변화 |
| Workflow | 실행 현실성 | 일상 업무 흐름과 속도 |
| Market-Policy | 버틸 수 있는가 | 향후 정책·규제·시장 충격 노출 |

원래 질문·점수 연결은 **Q18→Framework, Q19→Informal, Q20→Formal, Q21→Workflow, Q22→Market-Policy**이며, 각 질문에는 승인된 세 선택지와 0/1/2 점수표가 있습니다.

**중요:** 이 번호는 원래 구조화 설문 번호입니다. 현재 웹 설문에서 같은 번호가 같은 질문을 뜻하지 않습니다.

고객 설명문을 보고 점수를 추측하거나, 준비도·지원 수준·Safety Margin을 FIFWM 점수로 대체하거나, 미응답을 0점으로 만드는 것은 금지합니다.

### 3.3 현재 제품 적용 계층의 핵심 출력

현재 `ProductApplicationV3`의 분석 순서는 다음과 같습니다.

```text
User Input
→ Live External Evidence
→ FIFWM / Decision Structure
→ What You May Be Missing
→ Current Structural Posture
→ Changing
→ Safety Margin
→ Decision Switches
→ Next Experiment
```

각 단계의 의미는 다음과 같습니다.

| 항목 | 고객에게 제공해야 할 내용 |
|---|---|
| Decision Structure | Option A가 지키는 기반, Option B가 여는 가능성, 핵심 긴장과 제약 |
| What You May Be Missing | 판단을 바꿀 수 있지만 아직 확인되지 않은 핵심 조건 |
| Current Structural Posture | 현재 조건이 어느 방향을 지지하는지와 그 이유·위험·반대 근거 |
| Changing | A/B 중 하나를 고르는 것 외에 조건 자체를 조정하는 경로 |
| Safety Margin | 판단이 틀렸을 때 감당·회복·재진입할 여유 |
| Decision Switches | 어떤 조건이 달라지면 구조적 해석이 어떻게 바뀌는지 |
| Next Experiment | 확인할 질문, 모을 증거, 노출 한계, 계속·중단·재검토 조건 |

Changing에는 병행 검증, 역할 범위 조정, 시점 조정, 자원 재구성, 경로 조정 계열이 있습니다. **실제 근거에 따라 0~3개가 나와야 하며, 빈칸을 채우기 위한 기본 카드가 있어서는 안 됩니다.**

지속가능성 관점도 유지해야 합니다. 전환의 매력뿐 아니라 시간·자원·업무·생활 조건을 실제로 유지할 수 있는지 설명하되, 구현 공백을 메우기 위한 임의의 새 점수를 만들지 않습니다.

### 3.4 현재 계산에서 보존하고 점검할 부분

Safety Margin은 **Financial Room, Reversibility, Downside Exposure**를 구분합니다. 현재 코드에서는 알려진 차원만 계산하고, 2개 미만이면 `unknown`으로 남깁니다.

현재 V3 Posture는 기존 support 공식과 8/1 경계를 사용하며, 특정한 취약 안전마진·회복 가능성·하방 노출 조합에 guardrail을 적용합니다. 결과를 보기 좋게 만들기 위해 가중치·경계·guardrail을 임의 변경하지 않습니다.

일부 내부 계산에는 `unknown`의 중립 계산값으로 1을 사용하는 부분도 있습니다. **이 내부 계산값을 고객에게 “중간 수준으로 확인됨”이라고 전달하지 않는지** 점검해야 합니다. 미확인 상태와 근거 출처는 끝까지 유지해야 합니다.

## 4. 고객 결과물에 필요한 분석 구조

원래 보고서에는 다음의 논리적 역할이 있습니다.

**Executive Dashboard/Overview → 외부 조건 → 내부 위험 진단 → Career Value → Career Mobility → Strategic Temperament → 점수화 종합 → 제한된 검증 계획 → Decision Conditions.**

단일 사례는 `External Snapshot`, 비교 사례는 `External Comparative Snapshot`을 주 외부 섹션으로 사용합니다. 둘을 중복된 주 섹션으로 늘어놓지 않습니다. 비교는 표가 중심이고 짧은 해석이 보조입니다. 외부 맥락의 네 축은 **Market Direction, Competition Pressure, Economic Pressure, Transition Friction**입니다.

V2에서 이 내용을 고객 여정에 맞게 재배치할 수는 있습니다. 그러나 **새 화면에 카드가 있다는 이유로 원래 분석이 구현됐다고 판단하면 안 됩니다.**

결과물의 최소 연결 단위는 다음과 같아야 합니다.

```text
확인된 공개 사실
→ 해당 사실의 적용 범위
→ 고객의 현재 조건
→ 구조적 의미
→ 남아 있는 불확실성
→ 다음 검증
→ 조건 변화 시의 영향
```

예를 들어 과정의 시간·비용·평가 요구가 확인되고 고객이 보고한 시간 여유와 충돌한다면, 그 충돌과 검증 방법을 설명해야 합니다. “학위를 고민하고 있으므로 신중한 판단이 필요합니다”라는 재진술로 끝나면 분석이 아닙니다.

이 예시는 요구 품질을 설명하기 위한 것이며 특정 대학의 사실이나 새로운 점수 규칙을 제시하는 것이 아닙니다.

대시보드, 시뮬레이터, 보고서는 같은 기준 입력·근거 스냅샷·분석 결과를 공유해야 합니다. 언어를 바꾸거나 보고서를 여는 것만으로 근거와 기본 분석이 달라져서는 안 됩니다.

## 5. 코드와 파이프라인에서 혼동하면 안 되는 부분

### 5.1 세 경로를 구별할 것

**원래 보고서 경로:** 입력 정규화 → flags → 섹션 생성 → report/template payload → DOCX bridge → `merge_docx.py`.

**기존 웹 경로:** `/amc-web-mvp`. 29문항 기반 흐름과 ProductApplicationV3 연결 이력이 있습니다.

**실험 인터랙티브 경로:** V1은 15문항 계열이고, 현재 V2는 8단계 모듈 흐름이며 완료 메타데이터에도 8을 사용합니다.

README의 원래 보고서 경로를 현재 공개 V2 전체의 실행 경로라고 단정하지 마십시오. V2 화면, ProductApplicationV3 내부 모델, 원래 Python 엔진은 버전 체계도 서로 다릅니다.

**문항별 의미·타입·허용값·출처·결측 처리·사용처를 연결한 계약표가 필요합니다.** 운영 완료율에서도 29문항, 15문항, 8단계를 같은 분모로 취급하지 않는지 확인해야 합니다.

### 5.2 현재 V2에서 추적해야 할 흐름

```text
고객 입력과 동의
→ 사례 유형·공개 검색 대상·지역·범위 확인
→ 서버 전용 External Intelligence API
→ Perplexity 응답
→ 응답 구조·근거 카드·인용 검증
→ 공개 출처 접근성 검사
→ 사실·범위·confidence 정규화
→ 기존 structural signals와 ProductApplicationV3 연결
→ 비점수형 해석 계층
→ 대시보드·시뮬레이터·보고서
→ 허용된 운영 메타데이터 저장
```

현재 V2 공개 검색 요청의 허용 필드는 다음 다섯 개입니다.

```text
caseType
externalAreas
targetGeography
targetLabel
language
```

대상과 지역은 필수입니다. 학위 유형의 기본 검색 범위는 `programOutcomes`, `employmentRelevance`, `funding`입니다. **이번 학위 실패는 이 요청 범위와 실제 원문에서 추출할 수 있는 사실 사이의 관계부터 점검해야 합니다.**

고객이 외부 도구를 별도로 다루거나 검색 결과를 수동 전달해야만 분석되는 구조가 아니어야 합니다. 승인된 분석 동작으로 서버 검색이 이어져야 하고, 실제 진행 상태가 표시돼야 합니다. 시뮬레이터·언어 전환·보고서 열기마다 검색을 다시 해서는 안 됩니다.

## 6. 현재 점검 기준 버전

다음은 최신 PR #92에 기록된 기준입니다. 작업 시작 시 실제 branch, SHA, deployment, domain alias를 대조해 주십시오.

## 7. 현재 확인된 출시 차단 문제

### 7.1 외부 검색은 응답했지만 학위 사례의 근거 카드가 없음

2026년 10월 13일 검수 기록에 나타난 운영 로그입니다. 시간은 **UTC**입니다.

| 시각 | 앱 응답 | 공급자 응답 | 진단 | 근거 카드 | 검색 URL 수 |
|---|---:|---:|---|---:|---:|
| 14:06:58.004 | 503 | 200 | `source_unavailable / no_evidence` | 0 | 10 |
| 14:07:28.950 | 503 | 200 | `source_unavailable / no_evidence` | 0 | 10 |

이 기록이 말해주는 것은 **공급자 응답은 돌아왔지만 근거 블록이 없었다**는 점입니다. 실패는 출처 접근성 검사 이전에 발생한 것으로 기록돼 있습니다.

따라서 이것만으로 API 키 누락, 네트워크 타임아웃, 10개 출처 전체의 접근 실패, 실제로 정보가 전혀 없음을 결론내릴 수 없습니다. 요청 원문과 공급자 원문이 기록에 없으므로 **빈 배열이 나온 정확한 원인은 미확정**입니다. 두 요청의 사용자 동작 또는 재시도 경로도 별도 추적해야 합니다.

**요청:** 비식별 학위 재현 사례에서 기관·과정·지역·검색 항목을 명확히 하고, 요청 구성 → 검색 결과 → 근거 생성 → 정규화 단계를 구별해 조사하십시오. 가짜 근거나 일반론으로 성공 처리하는 수정은 불가합니다.

### 7.2 외부 분석 완료 전에 결과 화면이 열림

현재 `AmcInteractiveV2.tsx`의 `finish()`는 다음 순서로 동작합니다.

```text
setPhase("dashboard")
→ withEvidence일 때 void checkCurrentEvidence()
```

`Phase` 타입에도 별도의 processing 상태가 없습니다. 코드상 `dashboard_generated` 이벤트도 검색 완료 전에 기록됩니다.

즉 고객이 외부 근거를 포함한 분석을 요청해도 **검색 중에 결과 화면을 먼저 보게 되며, 완료 이벤트도 분석 완료와 혼동될 수 있습니다.**

**요청:** 실제 입력 검사 → 공개 검색·출처 확인 → 구조·조건 연결 → 완료 상태를 연결하십시오. 실패하면 재시도 또는 **“외부 근거 없는 구조 초안 보기”**를 명시적으로 선택하게 해야 합니다.

가짜 진행률, 강제 대기 시간, 분석하는 척하는 연출은 금지합니다.

### 7.3 9가지 사례 전체에 원래 평가 입력이 연결돼 있지 않음

현재 원래 FIFWM 질문이 허용되는 유형은 다음 세 가지입니다.

- Corporate Stay vs Exit
- Industry Transition
- Role Upgrade / Downgrade

이 세 유형에서도 목표 조직·직무가 확인되고 원래 유효 선택지가 입력돼야 합니다.

나머지 유형은 **Entrepreneurship, MBA / EMBA / PhD Decision, Overseas Relocation, Burnout-driven Decision, Family Constraint-heavy Decision, General Career Reconfiguration**입니다. 이 경로에서는 해당 조직·직무 평가가 `unavailable`로 남습니다.

이는 모든 분석 기능이 없다는 뜻은 아니지만, **전체 유형의 프레임워크 적용이 완성됐다는 뜻도 아닙니다.**

**요청:** 학위에 조직 질문을 억지로 대입하거나 새 점수를 만들지 말고, 원래 프레임워크 안에서 어떤 공개 사실과 승인된 개인 입력을 연결할지 정리하십시오. 새로운 질문·평가 규칙이 필요하면 별도 제품 승인 사항으로 올려야 합니다.

### 7.4 입력 재진술과 고정 문구가 분석처럼 보임

최신 검수 기록에서는 외부 근거 없는 학위 사례의 결과가 미리 작성된 case/band 문구와 자기보고 반복에 상당 부분 의존한다고 지적합니다. Safety Margin, Changing, 시나리오 계산은 실행되지만 기대한 근거 기반 학위 분석에는 못 미칩니다.

**요청:** “함수가 실행됐는가”와 “새로운 해석을 제공했는가”를 분리해 검수하십시오. 핵심 문장마다 근거·적용 범위·고객 조건·해석·불확실성·다음 확인 사항을 추적할 수 있어야 합니다.

비처방적 언어 원칙을 이유로 의미 없는 일반론만 제공해서도 안 됩니다.

### 7.5 최종 인쇄 보고서 품질 미달

고객 제출 학위 보고서에는 다음 문제가 기록돼 있습니다.

**8장 A4의 큰 빈 공간, 단일 Changing 카드의 부적절한 다중 카드 레이아웃, 반복적인 일반론, 두 자릿수 인덱스 줄바꿈, 외부 근거 조건이 연결되지 않은 관계도.**

`amcV2ReportDensity.ts`의 진단값이 존재한다고 레이아웃 품질이 보장되는 것은 아닙니다.

**요청:** 빈 상태·1개 카드·복수 카드·긴 한국어·근거 실패·부분 근거 상황에서 실제 인쇄물을 확인하십시오.

8장 또는 9장을 목표로 고정하지 마십시오. 논리적 섹션 수와 실제 PDF 페이지 수를 구별하고, 내용의 완결성·가독성·여백·잘림을 기준으로 판단해야 합니다.

### 7.6 한국어와 실제 PDF 저장 검증이 끝나지 않음

자유 입력에 고정 조사를 붙여 **“현재 직무와 생활 기반는”** 같은 문장이 생기는 문제가 최신 기록에 남아 있습니다. 이는 폰트·CSS만의 문제가 아니라 동적 문장 조립 문제입니다.

자동화된 인쇄 렌더와 브라우저 기본 Save/Cancel 동작도 별개의 검증입니다. 실제 저장 파일명, 취소 후 제목 복구, 최종 PDF의 물리 페이지와 잘림을 실제 브라우저에서 확인해야 합니다.

### 8.2 실패 단계가 다른데 같은 원인으로 처리하는 문제

API 라우트 누락, 인증, 공급자 오류, 빈 근거, 파싱 실패, 출처 접근 실패, 출처 내용 부적합, 프런트 상태 반영 실패는 서로 다릅니다.

이를 모두 **“외부 정보 없음”**으로 묶으면 같은 추측과 수정을 반복하게 됩니다.

과거에 DNS·주소 선택, 403, 로그인·가격 페이지 리다이렉트, HTTP 200이지만 내용이 없는 페이지를 조사한 기록이 있습니다. 그러나 이를 이번 공급자 `no_evidence`의 확정 원인으로 가져오면 안 됩니다.

또한 접근 가능한 URL이 해당 주장을 뒷받침한다는 뜻은 아닙니다. 직무 설명은 현재 채용 중이라는 증거가 아니며, 규제상 요구는 특정 상품의 유료 수요 증거가 아닙니다.

### 8.3 문서·코드·배포·검수 기준의 불일치

“완료”, “Ready”, “통과”라는 표현을 볼 때 반드시 **어떤 버전·환경·입력·검증 범위인지** 확인해야 합니다.

일부 문서는 중간 커밋이나 오래된 상품 정책을 기준으로 작성돼 있습니다. 완료 주장보다 실제 코드, 재현 결과, 최신 고객 수용 검수와 승인 이력을 우선하십시오.

### 8.4 이번 소스 확인에서 발견한 잠재적 타입 변환 위험

`amcProductApplicationV3.ts`의 `fifwmScore()`는 비숫자 입력에 `Number(value)`를 적용합니다. 이 경우 명시적 `null`, 빈 문자열, `false`가 0으로 변환될 수 있습니다.

**실제 고객 경로에 해당 값이 들어오는지와 결과 영향은 실행 검증하지 않았습니다.** 따라서 확정된 고객 장애가 아니라 추가 재현·단위 테스트 대상입니다.

유효 숫자 0과 결측값을 구별하는지 확인하되, 원래 평가표 자체를 변경하는 작업과 분리하십시오.

## 10. 요청하는 작업 순서

### 1단계 — 기준 상태 고정과 장애 재현

실제 공개 domain alias, SHA, branch, runtime route, 환경변수 이름과 적용 범위를 기록합니다. 비밀값은 출력하지 않습니다.

동의된 고객 자료 또는 비식별 입력으로 학위 실패 사례를 재현하고, 화면·요청·응답·운영 메타데이터를 같은 실행으로 연결합니다. 현재 호스팅·외부 API 한도, timeout, 비용 상한과 알림도 확인하되 승인 없이 구매·변경하지 않습니다.

### 2단계 — 외부 근거 경로와 완료 대기 수정

요청이 공급자까지 전달됐는지, 왜 근거가 비었는지, 어느 단계에서 데이터가 제거됐는지 구별합니다.

동시에 최종 화면과 완료 이벤트가 실제 분석 완료 전에 나가는 문제를 해결합니다. 무조건 성공하는 대체 응답이나 출처 검사 완화로 통과시키지 않습니다.

### 3단계 — 사례별 분석 적용과 데이터 계약 정리

9가지 사례별로 **입력 → 분석 항목 → 점수화 가능 여부 → 근거 → 고객 해석** 연결표를 작성합니다.

미적용·미확인·미응답을 구별하고, 기존 규칙을 바꿔야 가능한 부분은 별도 승인 항목으로 제출합니다.

### 4단계 — 공통 분석을 화면·시뮬레이터·보고서에 연결

입력 반복 대신 사실과 조건의 관계를 설명합니다. 외부 근거 변화가 영향을 줄 수 있는 항목과 영향을 주면 안 되는 항목을 구분합니다.

출처가 추가됐다고 개인의 적합성·준비도가 자동 검증된 것처럼 표시하지 않습니다.

### 5단계 — 실제 사용자 환경에서 최종 검수

한국어/영어, 모바일/데스크톱, 외부 근거 실패/부분 성공/성공, 실제 PDF 저장을 확인합니다.

일부 경로만 통과하면 전체 완료로 보고하지 말고, 통과한 범위와 남은 위험을 명시합니다.

| 외부 정보 | 검색 실행·근거 생성·접근성·주장 지원·개인 적용 범위를 구별함 |
| 처리 상태 | 외부 분석 전에 완료 표시·집계가 발생하지 않으며 실패 시 재시도/초안 선택이 명확함 |
| 사례별 적용 | 9가지 사례의 지원 범위와 미지원 평가가 명시됨. 두 데모만으로 전체 통과 판정하지 않음 |
| 점수·결측 | 원래 평가표 유지, 미확인·미적용·실제 0점 구별, 임의 추정 없음 |
| 분석 가치 | 사실·고객 조건·해석·불확실성·다음 검증이 연결됨 |
| 시뮬레이터 | 가정과 실제 기준선 분리, 원래 엔진 재평가, reset 복구, 원본 근거 불변 |
| 호출 관리 | 분석 동작과 호출 횟수 추적. 언어·시뮬레이터·보고서·인쇄에서 불필요한 추가 호출 없음 |
| 한국어/영어 | 의미·기준 결과 유지. 조사·동적 문장·줄바꿈 검수. 출처 번역 여부를 정직하게 표시 |
| 화면·PDF | 모바일·데스크톱, 0/1/복수 카드, 긴 입력, 실제 저장·취소·파일명·물리 페이지 검수 |
| 운영 데이터 | 허용 정보의 저장·조회 일치. 세션 전용 원문 비저장을 장애로 오인하지 않음 |
| 배포·접근 | 검수 SHA와 공개 도메인 SHA 일치. 검수자가 실제 사용할 수 있는 접근 경로 제공 |

현재 시뮬레이터의 원래 변수는 **재정 여유, 회복·재진입 가능성, 하방 노출, 내부 준비도, Option B 지원, 제약 부담, 외부 검증**의 7개입니다. 원래 민감도·시나리오 원칙을 유지하고, 고객 화면은 영향이 큰 소수 변수 중심으로 구성해야 합니다.

**모의 응답 테스트, 실제 공급자 호출, 출처 원문 검토, 실제 DB 왕복, 실제 PDF 저장은 각각 다른 증거입니다.** 실호출은 승인된 범위에서 최소화하고 정확한 횟수를 기록하십시오.

## 12. 개인정보·운영·변경 원칙

V2의 자유서술과 개인 비교 메모 등은 세션 내 메모리 중심의 비저장 계약을 따릅니다. **“session-only”를 원문을 모두 `sessionStorage`에 저장해도 된다는 뜻으로 해석하지 마십시오.** 여정 식별자와 원문 답변의 저장 정책도 다릅니다.

외부 제공자에는 승인된 공개 검색 맥락만 전달합니다. 문제를 빨리 해결한다는 이유로 고객의 전체 답변·사적 메모·내부 분석문을 전송하거나 로그에 남기지 않습니다.

서비스 운영 동의와 선택적 연구 동의를 구별합니다. 운영상 허용된 메타데이터는 저장 성공·실패·미저장을 구분해 확인해야 합니다. **health 200만으로 저장 성공을 주장하지 않습니다.**

안전장치, 출처 검증, 개인정보 경계를 해제해 테스트를 통과시키지 않습니다. 별도 승인 없이 프레임워크·점수·경계·동의 문구·키·환경 범위·DB 스키마·공개 도메인·JEV·Production 배포를 변경하지 않습니다.

작업은 원인별로 검증 가능한 단위로 나누고 다음을 제출해야 합니다.

```text
수정 전 재현
→ 수정
→ 수정 후 테스트
→ 회귀 검수
→ 변경 내역
→ 남은 위험
```

## 13. 엔지니어에게 요청하는 최종 산출물

**① 현행 아키텍처와 실행 경로**  
고객 URL부터 API, 외부 공급자, 분석, 보고서, 운영 저장까지의 연결과 책임 경계.
